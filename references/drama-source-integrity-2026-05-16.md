# 追剧换源完整性校验补充（2026-05-16）

## 触发背景
用户明确指出：
- 不能只靠 `current/total` 数量判断要不要继续追剧
- 网上/元数据已经显示“更新完了/已完结”的剧，如果本地还在追，更可能是**当前资源源不完整**
- 这类问题应优先做“换完整源”，而不是只改 state

## 本轮验证到的具体现象
### 1) `share-source-recovery.py` 旧逻辑缺陷
旧逻辑允许在 `apply` 时直接切到候选源，只要候选存在即可；**没有校验候选真实集数是否满足 `expected_total`**。

### 2) 实测反例
- `佳偶天成`
  - 官方总集数：40
  - 恢复候选实际核验：23 集
  - 旧逻辑会直接切换，导致 state 仍记 40，但源只剩 23
- `黑夜告白`
  - expected_total: 28
  - 候选核验：15 集
  - 明显不能切
- `良陈美锦`
  - expected_total: 36
  - 看起来是“稳定目录”候选，但递归核验后只有 19 集
  - 证明“稳定目录 ≠ 完整目录”

## 已沉淀规则
1. **官方/元数据完结优先于资源当前集数表象**
   - 若元数据已完结，但本地 ongoing 且 current < total，不要直接判定“还在更新”
   - 优先怀疑：当前绑定 `source_path` 是残缺源/错源

2. **换源前的硬门槛**
   - 候选源必须先递归核验实际可播放视频数
   - 若 `actual_count < expected_total`：
     - 禁止自动 apply
     - 保留待恢复项
     - 报告为“源不完整，需继续搜完整源”

3. **稳定目录也要核验**
   - `每日更新/...`、`同步更新中/...`、非分享目录，都不能因“路径稳定”就默认合格
   - 必须像分享源一样递归数视频文件并抽样验证可播放性

4. **追剧误留在 ongoing 的一类典型根因**
   - 不是 reconcile 没清掉
   - 而是：官方已完结，但 state 绑定的是不完整资源，导致系统持续把它当作“差几集待更新”

## 适用排查顺序
1. 查 `status / total_episodes / total_evidence`
2. 查 `current_episodes / source_entries`
3. 查当前 `source_path` 真实视频数与可播放性
4. 若元数据已完结但源不满集，进入全库/网盘换源
5. 只有候选满足 `expected_total` 才允许 apply
6. apply 后重新 reconcile + list 验证是否仍 ongoing
